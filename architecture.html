01 / SYSTEM OVERVIEW

One controller connects two independent tools

The model interprets language and proposes SQL. PostgreSQL performs the arithmetic. Python controls execution, checks statements, and manages failures.

Arrows show calls and dependencies; results return to callers. Dashed line represents logging across the run. Schema reads happen before a cache lookup, so a cache hit still needs PostgreSQL.

Startup wiring

main.py → cli.main() → load_settings() → build_agent(). The CLI builds one clock, logger, model client, database adapter, cache, generator, executor, and orchestrator. Dependencies are passed into constructors.

Local runtime

The Python process calls the configured Ollama host and PostgreSQL server. Defaults use localhost. Environment variables supply configuration; no web server, frontend framework, or agent framework is required.

02 / COMPLETE REQUEST FLOW

From user input to streamed response

Interactive input, a one-shot question, and --file all follow this flow. Model names below reflect the current configuration and default: qwen2.5-coder:7b.

1 · Check relevance

Log the question, assign a run ID, and classify scope before any database access. Only a valid JSON decision with allowed=true proceeds.

CLI: input / question / --file
  → Orchestrator.run(question, on_token=emit)
  → log question + assign run_id
  → Scope guard [qwen2.5-coder:7b; buffered JSON]
      blank / denied / invalid JSON / unavailable → refusal + error log → exit 1
      allowed=true
        → Router [qwen2.5-coder:7b; buffered JSON]: generate_sql
        → Generator: live schema + samples → SQL cache lookup
            hit  → reuse SQL (no SQL-writer call)
            miss → SQL writer [qwen2.5-coder:7b; buffered text] → extract SQL
            SELECT 'UNSUPPORTED' → refusal, no execution/cache write
        → Router: execute_sql
        → SQL guard → PostgreSQL transaction → bounded rows / row count
            failure → retry counter + cache eviction/bypass
                    → generate with previous SQL + error (bounded retry loop)
            success → cache successful SQL
        → Router: final
        → SELECT / returned columns:
            answer writer [qwen2.5-coder:7b; stream=True]
            → text chunks → on_token → print(end="", flush=True)
            → accumulated answer + log + AgentResult
          INSERT with no returned columns:
            → Python Saved message → on_token (no answer-model call)
        → CLI prints SQL + run metadata once → exit 0
  1. Scope: permit reading and adding expense records, including terse notes. Deny unrelated requests, mixed tasks, destructive changes, and attempts to override instructions. A classifier error fails closed. Cache hits still require this check.
  2. Routing: Python preserves the original question and SQL. The model selects actions only. An invalid action order triggers the existing state-machine recovery.
  3. Generation: schema text contains live columns, comments, and up to three samples per table. Cache keys include normalized question, schema, model, and today’s date. Only successfully executed SQL is cached, never results.
  4. Execution: validate one SELECT/WITH/INSERT statement. SELECT is read-only; writable transactions commit INSERTs on success and roll back exceptions. Retain up to 100 rows, with up to 20 described to the answer model by default.
  5. Response: stream only final answer text. Routing JSON and generated SQL remain buffered. The CLI displays the answer once, then SQL and run metadata. Ordinary INSERTs use the affected-row count directly.
  6. Recovery: two SQL retries allow up to three failed execution attempts within a ten-step overall budget. Empty or initially failed answer streams fall back to a table. Interrupted partial answers produce a failure message. The scope check is outside the routing step budget.
Model-call count: a normal uncached SELECT uses one scope call, three router calls, one SQL-writing call, and one answer call: six total. A cache hit uses five. An ordinary uncached INSERT uses five because no answer-model call is needed. A denied nonblank request uses one scope call and no database access. Retries can increase these counts.

02A / MODEL ROLES & STREAMING

One configured model, four separate prompts

OLLAMA_MODEL=qwen2.5-coder:7b is the current local setting and the default in config.py and .env.example. There are no separate router, SQL, guard, or answer models. Streaming contract

OllamaClient.chat_stream() calls Ollama with stream=True, yields nonempty chunk.message.content values, and wraps connection or iteration errors as LLMError. The orchestrator calls on_token(chunk) as chunks arrive, accumulates the same text in AgentResult.answer, and logs the complete successful answer. Calling run(question) without a callback preserves buffered behavior for Python callers.

python main.py "total spend today"              # streaming by default
python main.py --file notes.txt                 # same guard and response path
python main.py --no-stream "total spend today"  # buffered answer
python main.py --no-cache "total spend today"   # guard still applies

Streaming starts after scope checking, routing, and database work. It improves answer delivery while tokens are generated; it does not remove earlier model latency. Empty output or a failure before any answer chunk uses a plain table. A failure after partial output reports an incomplete answer and returns ok=False; the CLI preserves the displayed prefix and adds the error. Successful output is never printed twice.

Guard limitations: relevance is a model classification, not a security guarantee. Deterministic tests verify strict decision handling and blocked tool access, using model doubles. They do not prove real-model resistance to every prompt injection. SQL validation and database transaction checks remain separate protections.
SCHEMA CONTEXT

How does the LLM know the schema?

Python queries PostgreSQL and inserts a text description into the SQL writer’s system message. The LLM does not connect to PostgreSQL or read the SQL files itself.

  1. SqlGeneratorTool.run() calls self._db.get_schema() before checking its cache.
  2. _COLUMNS_QUERY joins pg_attribute, pg_class and pg_namespace. It reads ordinary tables in the configured schema, ignores dropped/system columns, and retrieves formatted types plus col_description().
  3. get_schema() groups those rows into a text block per table. _sample_block() optionally appends recent-looking rows by ordering the first column descending; in expenses that column is the generated ID. This is ID order, not expense-date order.
  4. SQL_SYSTEM_PROMPT.format(today=..., timezone=..., schema=...) inserts that text. The request is sent separately as a user message. On a cache hit, SQL generation is skipped; the freshly read schema still contributes to the key.

Illustrative schema text, with sample values omitted

TABLE expenses (
  id bigint  -- auto-generated, never set it
  spent_on date  -- date of the expense, YYYY-MM-DD
  amount numeric(12,2)  -- amount in BDT, always positive
  category text  -- one of: food, transport, bills, shopping, health,
                 education, entertainment, transfer, other
  note text  -- short free text such as lunch or rickshaw
  created_at timestamp with time zone  -- row creation time,
                                         auto-generated, never set it
)
-- Optional sample rows follow here when enabled and available.
Important distinction: this is a schema summary, not the complete CREATE TABLE definition. The query does not retrieve CHECK constraints, defaults, primary/foreign keys, indexes, or the table-level comment. Column comments supply much of the semantic guidance, including BDT and categories. PostgreSQL still enforces the actual constraints during execution.

The scope guard sees only its policy and the raw request. Only the SQL writer gets the full schema block. The router sees action descriptions and observations; the answer writer sees the question, generated SQL and a bounded result description. All roles use the same model client, but their message lists are separate. This is prompt context, not training or persistent model memory.

MODEL OUTPUT CLEANUP

Markdown is removed from SQL, not rendered

The expense app is a terminal program. It has no Markdown renderer. guards.extract_sql() cleans the SQL writer’s text before the executor validates it.

  1. Trim whitespace. Look for a triple-backtick fenced block using _FENCE; when present, take its content. Otherwise remove triple-backtick markers. An alphabetic language tag such as sql is supported.
  2. Drop introductory text. Search for the first WITH, SELECT or INSERT keyword and keep text from that position onward.
  3. Keep the first statement. Mask string literals, quoted identifiers and comments before finding the first semicolon. This prevents a semicolon inside a note string from terminating the SQL.
  4. Validate separately. The executor applies statement classification and rejection rules. Cleanup is not SQL validation or a guarantee of correct interpretation.

Possible model response

Here is the query:
```sql
SELECT category FROM expenses;
```
This lists expense categories.

Extracted SQL

SELECT category FROM expenses

The surrounding prose, fence, and terminating semicolon are removed.

Actual extraction function from guards.py 
def extract_sql(raw: str) -> str:
    """Pull one bare SQL statement out of whatever the model returned.

    Small models often wrap SQL in markdown fences, add 'Here is the query:' in
    front, or explain it afterwards. All of that is removed here.
    """
    text = raw.strip()
    fenced = _FENCE.search(text)
    text = fenced.group(1).strip() if fenced else text.replace("```", "")

    start = _SQL_START.search(text)
    if start:
        text = text[start.start():]

    end = _mask(text).find(";")
    if end != -1:
        text = text[:end]
    return text.strip()
Limits worth understanding: extraction silently discards later statements after the first semicolon, while direct validation rejects multiple statements that reach it. The keyword search can mistake a keyword in introductory prose for SQL. Explanations without a separating semicolon may remain and cause a database error. This is deliberately small cleanup code, not a general Markdown parser.

Final answers: cli._run_request() flushes streamed chunks and _print_result() displays metadata. With --no-stream, the completed answer is printed at once. Markdown in answer-model output is printed literally; it is not stripped or rendered. The fallback table is plain text separated by pipes.

This guide: browser rendering comes from HTML, CSS and inline SVG. Code appears inside escaped <pre><code> elements. Walkthrough text is assigned through textContent, so it is not interpreted as HTML or Markdown.

Calculation responsibility

Database arithmetic, model wording

PostgreSQL filters expense rows and calculates totals using exact decimal amounts. The answer model turns returned rows into prose. To verify a result, compare the matching rows and date boundaries against the SQL; a successful query alone does not prove the intended question was answered.

Current behavior

Date and currency gaps

The prompt defines “last N days” as spent_on >= CURRENT_DATE - N. For N = 10 that covers eleven calendar dates including today and has no upper bound. The answer writer receives results but no currency metadata, so it may incorrectly print a dollar sign.

-- Proposed: exactly ten calendar dates, including today
SELECT COALESCE(SUM(amount), 0) AS total
FROM expenses
WHERE category = 'food'
  AND spent_on BETWEEN CURRENT_DATE - 9 AND CURRENT_DATE;

SUM performs the addition; COALESCE returns zero when no rows match. The seed rows do not exercise every date boundary, so they cannot alone establish that the range is correct. Use separate boundary fixtures instead of relying on a sample spending total.

Current configuration: the setup SQL now uses the existing postgres account. The earlier restricted expense_agent grants were removed. Database permissions therefore do not limit the application to SELECT and INSERT. Some README text and the guard module’s introductory comment still describe the previous restricted-role design.
  • Request guard: relevance.check_relevance() checks scope before tools or database access. Only a literal boolean true allows the request; blank, denied, malformed, or unavailable classification is rejected and logged.
  • SQL guard: masks quoted text and comments, classifies SELECT/WITH/INSERT, rejects multiple statements, forbidden keywords, selected function names, SELECT INTO, and malformed quoting. Extraction keeps the first statement before validation.
  • Limit: this is regex-based filtering, not a full SQL parser or table/function allowlist. Quoted identifiers are masked, so identifier checks are incomplete. A permitted SELECT or INSERT can target unintended objects accessible to its database account.
  • Database: SELECT executes read-only. INSERT must execute writable, so it particularly depends on privileges and validation. Constraints enforce required fields, categories, and positive amounts, but cannot verify the meaning of a user request.
  • Resource bounds: the statement timeout defaults to 5 seconds; at most 100 result rows are retained and 20 sent to the model. Fetch limits do not eliminate expensive database scans or aggregation work.
  • Answer reliability: the answer prompt says to use only results, but generated wording is not checked for currency, arithmetic, or misleading summaries of truncated results.
  • Duplicate writes: repeated INSERT requests add rows again. A cache hit reuses SQL text; it does not make writes idempotent.

FINAL / PROJECT-SPECIFIC NEXT STEPS

Steps to improve this project’s results

These are proposed examples, not changes to the running application. Prioritize date boundaries and BDT formatting, then add focused regression cases before adjusting the existing prompts and controller. The snippets below fit this codebase and do not require a new framework.

1. Make the date rule explicit and invalidate old cached SQL Proposed · tools.py / cache key

Choose a clear product rule: “last N days” includes today and the previous N−1 calendar dates. Update both the SQL prompt rule and its example. Add a prompt version to the cache key so previously generated SQL is not reused after changing instructions.

# tools.py: add near SQL_SYSTEM_PROMPT
SQL_PROMPT_VERSION = "v2-calendar-days"

# Inside run(), replace the existing build_key(...) call:
key = build_key(
    normalize_question(question), schema, self._llm.model,
    self._clock.today().isoformat(), SQL_PROMPT_VERSION,
)

# New prompt rule and example:
# last N days: spent_on BETWEEN CURRENT_DATE - (N - 1) AND CURRENT_DATE
# last 10 days: spent_on BETWEEN CURRENT_DATE - 9 AND CURRENT_DATE

Verify: rows at today−9 and today must be included; rows at today−10 and tomorrow must be excluded. Test a single-day request too. Prompt instructions guide generation; inspect generated SQL to verify compliance.

2. Format simple totals in Python with BDT Proposed · orchestrator.py

A deterministic formatter prevents an invented dollar sign for a known one-column total. Add this before the answer-model call in _compose_answer(); keep the existing model path for other result shapes. The alias is a convention, so this narrow handler should be used only for monetary-total queries.

from decimal import Decimal

# Inside _compose_answer(), after the no-columns INSERT branch:
if (result["columns"] == ["total"]
        and len(result["rows"]) == 1
        and len(result["rows"][0]) == 1
        and result["rows"][0][0] is not None):
    amount = Decimal(str(result["rows"][0][0]))
    return f"Total spending: BDT {amount:,.2f}."

Also add the BDT currency instruction to the answer prompt for other shapes. For broader use, introduce an explicit result type such as “money_total” rather than relying on the alias alone. Verify zero, decimals, and large totals.

3. Use a fixed controller when the workflow is always the same Proposed · orchestrator.py

The existing _default_action() already knows the normal sequence and repair path. If model-driven routing is not required, replace the body of _decide() with this simpler implementation. The SQL model remains responsible for interpreting the user’s request.

def _decide(self, messages, state, run_id, step):
    action = self._default_action(state)
    self._logger.log(
        "decision", run_id, step=step,
        action=action, source="state_machine",
    )
    return action, "next action follows the current run state"

This removes normal router calls and JSON parsing failures. Keep model routing if demonstrating agent tool selection is an explicit requirement or the available workflows become more varied.

4. Prevent the same successful INSERT from executing twice in one run Proposed · orchestrator.py

The router can currently choose execute again after success. Add a check near the start of _do_execute() so a repeated choice does not repeat a completed write.

if state.last_result is not None:
    return self._reject_choice(
        state, "This SQL already succeeded. Choose final."
    )

This guards the immediate repeat only. For stronger protection, make write success terminal or track completed writes separately so regeneration cannot reset the protection. Separate user submissions still require a request ID and a database uniqueness rule if deduplication is desired.

5. Use parameterized SQL for a small set of common requests Proposed · database adapter extension

A plain function can answer a supported total query without model-generated SQL. Validate inputs and bind values through psycopg; do not interpolate user text into SQL.

def food_total(conn, days: int):
    if not 1 <= days <= 366:
        raise ValueError("days must be between 1 and 366")
    with conn.cursor() as cur:
        cur.execute(
            """SELECT COALESCE(SUM(amount), 0)
               FROM expenses
               WHERE category = %s
                 AND spent_on BETWEEN CURRENT_DATE - %s
                                  AND CURRENT_DATE""",
            ("food", days - 1),
        )
        return cur.fetchone()[0]

This example needs a connection configured with the application timezone. The current run_sql() accepts only raw SQL, so integrating templates requires a parameter-aware adapter method or a separate repository function. Templates improve predictability but cover fewer question types.

6. Strengthen database isolation when moving beyond a local demo Optional future deployment change

The current user choice is postgres. If a restricted account becomes appropriate later, provision it once with an administrator, grant only the application objects it needs, and change the application DSN. This is a future option, not a change made by this guide.
